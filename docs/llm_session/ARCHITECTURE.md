# 代码架构调研与演进路线（R-21）
> 调研目标：选择能更好兼容后续新功能/新改动的架构，并落地第一步迁移。最后更新：遗漏批次迭代16。

## 一、现状问题
- `server/game/game.mjs` 原为约 1360 行巨型类：回合/战斗/法术/道具/对话/升级/传送/结算/快照全部耦合在 `Game` 一个类里。
- 实体（玩家/怪物/NPC）是内联对象字面量，行为散落在各处方法中；新增一个系统就要在一个文件里翻找所有相关方法。
- 风险：任何新功能（新职业特性、新怪物行为、新剧情机制）都要改动核心文件，回归面大。

## 二、调研对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **完整 ECS**（实体=ID+组件数组，系统遍历组件集） | 数据/逻辑彻底分离；海量实体下缓存友好；系统可并行 | 回合制跑团实体量小（几十个），缓存优势用不上；5E 规则天然"状态+行为"强耦合，组件爆炸（每个法术/特性一组组件）；LLM 导演、快照广播、回合看门狗等横切逻辑在纯 ECS 里很别扭；全量重写风险高 | ❌ 不采用纯 ECS |
| **Hybrid/轻量 ECS**（实体纯数据 + 系统函数 + 单编排器） | 保留 ECS 核心思想（数据与逻辑分离、系统独立可插拔）；改造渐进、可按系统逐块迁移、随时可回归 | 需要纪律：系统间共享状态要走编排器，避免暗中耦合 | ✅ **采用** |
| 维持单文件大对象 | 改动最小 | 无法解决"新功能兼容"诉求 | ❌ |

**选型结论**：采用 **Hybrid ECS（系统-组件式）**——实体保持纯数据对象（组件式字段），逻辑按领域拆成**系统模块**，`Game` 类只做**编排器**（持有状态、挂载系统、驱动快照与广播）。这是"ECS 的核心收益（系统独立演进）与回合制游戏实际需求"的平衡点。

## 三、目标目录结构
```
server/game/
  game.mjs          编排器：状态容器 + 系统挂载 + 快照/广播（已从1364行降至1097行）
  entities.mjs      实体系统：实体工厂（玩家/怪物/NPC）+ 空间查询（entitiesAt/pathMap/随机落脚点）
  systems/
    dialogue.mjs    对话系统：NPC对话树/门/宝箱/出口/篝火互动
    progress.mjs    进度系统：升级/短休/章节目标/出口传送
    turn.mjs        （下一步）回合/先攻/怪物AI/回合看门狗
    combat.mjs      （下一步）攻击/施法/伤害/死亡豁免/倒地
    goals.mjs       （下一步）隐藏目标/宣称/公开胜利判定
    snapshot.mjs    （下一步）快照组装
```

## 四、已完成的迁移（迭代16）
1. `entities.mjs`：实体工厂与空间查询全部迁出（实体=纯数据组件式对象）。
2. `systems/dialogue.mjs`：actInteract/_openDialogue/actDialogueOption（NPC 对话、门、宝箱、出口、篝火）。
3. `systems/progress.mjs`：_levelUp/actShortRest/_checkChapterObjective/_tryTravel。
4. `Game` 构造函数以 `installXxx(this)` 挂载系统；对外接口（rooms.mjs 调用的 actXxx 等）零变化。

## 五、迁移纪律（后续系统迁移必须遵守）
1. **逐块搬移、逐块回归**：一次只迁一个系统，搬完立即跑 solo-probe/sim/e2e。
2. **零行为变化**：迁移只搬代码不改逻辑；bug 修复与迁移分离提交。
3. **共享状态显式化**：系统只通过 `this`（编排器状态）与参数交互；系统间禁止互相 import。
4. **新功能落位**：新职业特性→combat 系统；新怪物行为→entities/combat；新剧情机制→dialogue/progress。
5. **验证基线**：game-smoke（引擎冒烟）+ solo-probe（单人全流程，覆盖对话/传送/升级）+ sim + e2e。
